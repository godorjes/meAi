## 1. 数据保护标准

保护对象：用户消息、已持久化的助手回复、未发送草稿、服务配置、API Key、会话标题和来源关系。模型目录可以重新读取，但刷新不能破坏上述数据。

正常关机、重启、清后台、强行停止、系统回收、崩溃和覆盖升级后，已经确认保存的数据必须完整恢复。数据库无法打开、磁盘写入失败或密钥解密失败时，保留原数据并明确报错，不返回假装正常的空数据库，也不覆盖为空值。

写入流程必须是：收到输入／片段 → 持久化事务提交成功 → 界面确认已保存。助手正文采用可靠提交后展示，使已展示回复有明确持久化依据。

草稿输入控件会先接收按键，突然断电前最后一个尚未提交字符无法直接承诺绝对不丢。应取消等待停止输入才保存的机制，尽快顺序提交，明确保存中／失败／已提交边界。该边界不能用于放宽已经确认保存的数据保护要求；硬件损坏同样不作绝对保证。

## 2. 推荐实施顺序

### A. 阻止升级清库，建立无损迁移基线（P0）

涉及：
- app/src/main/java/app/polyglot/dev/PolyglotApp.kt
- app/src/main/java/app/polyglot/dev/data/local/AppDatabase.kt
- app/build.gradle.kts
- 新增 app/src/main/java/app/polyglot/dev/data/local/DatabaseMigrations.kt
- 数据库迁移测试放入 app/src/androidTest/java/app/polyglot/dev/data/local/

- [ ] 从旧版本工程产物或测试数据库核对实际 schema。不能凭猜测编写 version 1 的迁移 SQL。
- [ ] 对已有数据取得一致性快照；数据库仍在写入时不能只复制 .db 而遗漏 WAL。备份留在本机受控位置，不输出密钥或聊天正文。
- [ ] 启用 Room schema 导出，保存旧版本 schema 与测试数据库。
- [ ] 先建立升级测试：预置会话、消息、草稿和配置，升级后逐项比较 ID、正文与关系。
- [ ] 移除 fallbackToDestructiveMigration，为受支持版本提供显式迁移。失败时保留原文件并提示恢复错误，不能自动重建。
- [ ] 测试迁移失败、重复启动及重新打开数据库；全部通过后才覆盖安装到已有数据的应用。

不要仅删掉 fallback 却不提供迁移，否则旧用户可能打不开数据库。

### B. 配置与密钥原子保存（P0）

涉及 KeyCrypto.kt、ConfigRepository.kt、Entities.kt、Daos.kt、AppDatabase.kt 和任务 A 的迁移文件。

推荐保留当前 Keystore 别名及 AES-GCM，加密后的 API Key 放入 Room 服务密钥表，与配置元数据在同一事务提交，数据库中不保存明文 Key。

- [ ] 先完成新密钥表的 schema 迁移；不删除或重建现有 Keystore 密钥。
- [ ] 加密在事务前完成；加密失败不修改原配置；事务提交成功后才报告保存成功。
- [ ] 旧 SharedPreferences 密文迁移必须可重复执行：新记录存在则跳过；提交成功且验证解密后才清理旧密文；中断后继续。
- [ ] 编辑／删除配置与会话引用更新采用事务；统一拦截修改正在被生成请求使用的配置。
- [ ] 测试加密前后、事务中、提交后、旧密文清理前后中断，确认恢复得到完整旧状态或完整新状态。

只把 apply() 改成 commit() 不足以让数据库与偏好文件形成同一个事务。

### C. 发送与草稿一致性（P0）

涉及 ChatRepository.kt、Daos.kt、ChatViewModel.kt、PolyglotApp.kt；新增 app/src/main/java/app/polyglot/dev/data/repo/GenerationCoordinator.kt。

- [ ] 在发送入口第一次挂起前占用单请求状态，并通过串行协调／互斥阻止连点重复请求。
- [ ] 新建会话、用户消息、助手待回复记录、请求关联 ID、清理本次发送草稿，作为一个 Room 事务提交。
- [ ] 提交成功后才开始网络请求；失败则保留输入、恢复按钮、明确提示保存失败。
- [ ] 草稿带会话 ID 与递增版本，顺序写入，旧版本不能覆盖新版本；取消“每次输入取消上次任务并等待 400ms”的方式。
- [ ] 发送只清理对应版本草稿。期间新输入、其他会话草稿和空聊天页独立草稿不能被清掉。
- [ ] 验证连续输入期间退出、事务中断、发送期间继续输入、快速切会话及连点发送／重试，检查无丢失、无重复、无串会话。

应用范围协程使写入不依赖页面是否还存在，但不能在进程死亡后继续运行，仍须依靠已提交磁盘数据。

### D. 流式回复、停止与启动恢复（P0）

涉及 OpenAiClient.kt、GenerationCoordinator.kt、ChatRepository.kt、ChatViewModel.kt、PolyglotApp.kt、MainActivity.kt。

- [ ] 流式增量有序持久化，再由数据库 Flow 展示。允许小批量提交，但未提交批次不能展示为已保存正文。
- [ ] 流式通道实行背压并检查交付结果；不能忽略 trySend 失败而静默丢片段。写入失败停止请求并报告，保留最后可靠提交的数据。
- [ ] 明确区分协议完成与提前断流，截断回复不能标记 DONE。
- [ ] 用户停止标记 STOPPED，退后台／锁屏标记 INTERRUPTED；合作式取消用 NonCancellable 完成必要收尾。强杀不能依赖收尾代码。
- [ ] 启动恢复完成前禁止新生成，把遗留 GENERATING 改为 INTERRUPTED，不自动重发。
- [ ] 恢复未过期删除时同时恢复待撤销实体与剩余计时；无配置仍允许阅读历史。
- [ ] 最后一轮 STOPPED／INTERRUPTED 可重试，复用原问题和上下文；新正文首段提交前保留旧部分回复。
- [ ] 用可控流验证密集片段、暂停、提前断流、停止、后台、强停，比较提交正文与恢复正文。

后台保活和 NonCancellable 均不能代替可靠持久化。

### E. 验证断电持久性及存储失败（P0）

- [ ] 检查实际 journal_mode 和 synchronous；WAL 模式采用满足每次提交同步要求的 FULL 策略，验证对实际连接生效，不只执行一次未经验证的 PRAGMA。
- [ ] 测量持续输入、长回复的提交性能，磁盘 I/O 不阻塞主线程，不能为流畅静默降级持久性。
- [ ] 测试空间不足、写入异常：不提示保存成功、不覆盖旧数据、不自动清库。
- [ ] 分别验证普通重启、系统回收、force-stop 与非正常退出；普通 ADB reboot 不能等同突然断电。
- [ ] 断电级验证使用专用测试设备／隔离数据，不拿用户唯一数据副本做破坏性试验。
- [ ] 报告测试通过范围和未覆盖条件。仅用了 Room 或仅通过一次重启都不能证明绝对零丢失。

SQLite 说明 WAL + NORMAL 在断电／系统崩溃后可能回滚近期事务；FULL 加强每次提交同步，但仍依赖操作系统和存储正确履行同步请求。
[SQLite 同步策略](https://www.sqlite.org/pragma.html#pragma_synchronous)

### 6.3 必须知道的遗留问题

- **用户 API Key 已不可解密，需要重新填写。** 运行 `connectedDebugAndroidTest` 时 Gradle 会在测试结束后卸载应用，
  应用私有数据被删除，Android Keystore 中的包装密钥也随卸载销毁。聊天记录、会话、配置元数据、模型目录
  已从升级前的一致性快照完整还原（五个表内容哈希与升级前逐字一致），但密钥密文再也解不开。
  **后续跑仪器化测试请改用 `adb shell am instrument`**，不要用 `connectedDebugAndroidTest`。
- 无法解密的历史密钥密文没有被删除，仍留在 `shared_prefs/polyglot_secure.xml`，符合「解密失败保留原数据」。
  用户在配置页重新填写并保存后，新密钥会写入数据库并清理该旧条目。
